# Implementation Plan: Phase-1.3 — Onboarding & Twin Bootstrap
## Plan ID: Phase-1.3-P1

## Sub-Phase Reference
Sub-Phase ID: Phase-1.3
Sub-Phase Title: Onboarding & Twin Bootstrap

## Objective
Deliver the complete onboarding flow and its supporting read/write endpoints in a single coherent plan. The `POST /athletes/{id}/onboarding` endpoint executes one atomic database transaction that creates or updates six domain entities, flips the onboarding gate, and emits `onboarding_completed` via the transactional outbox. The plan also delivers the lightweight GET/PATCH endpoints for profile, preferences, twin state and twin history that rely on the repositories built for onboarding. Together these form the first surface that writes real domain state; all prior sub-phases established schema only.

## Scope
- New repositories: `AthletePreferencesRepository`, `TrainingGoalRepository`, `AthletePhysiologyRepository`, `AthleteFitnessRepository`, `TwinStateRepository` — following the established pattern (`get`/`add` methods, `AsyncSession`, flush, no commit).
- New service: `OnboardingService` — hosts the atomic onboarding transaction, the read endpoints for onboarding status, profile, preferences, twin state, twin history, and the PATCH helpers for profile and preferences.
- New domain-error module: `app/services/onboarding_errors.py` with error classes mapping to HTTP 409 / 404 / 422 for onboarding, profile/PATCH and twin read paths.
- New request/response schemas for onboarding (request, response, status), profile (response, patch), preferences (response, patch), twin state (latest response, history response).
- New API router `app/api/v1/onboarding.py` registering:
  - `POST /athletes/{athlete_id}/onboarding`
  - `GET  /athletes/{athlete_id}/onboarding`
  - `GET  /athletes/{athlete_id}/profile`
  - `PATCH /athletes/{athlete_id}/profile`
  - `GET  /athletes/{athlete_id}/preferences`
  - `PATCH /athletes/{athlete_id}/preferences`
  - `GET  /athletes/{athlete_id}/twin`
  - `GET  /athletes/{athlete_id}/twin/history`
- Router and export registrations: `app/repositories/__init__.py`, `app/schemas/__init__.py`, `app/services/__init__.py`, `app/api/v1/__init__.py`, and the `build_onboarding_service` + related deps on `app/api/deps.py`.

## Out Of Scope
- `fitness_improvement`, `maintenance`, `recovery` goal types — the TrainingGoal model accepts the enum members but the onboarding path must reject them.
- `Objective` seeding — deferred to Phase 4.
- Menstrual cycle tracking (`CyclePhaseLog`) — deferred to Phase 3.
- `WeeklyPlan` creation (plan generation — sub-phase 1.4).
- First coach message generation (sub-phase 1.5a).
- Any change to existing models, migrations, or schema — all six tables are created by Phase 1.2a / 1.2b / 1.2c and the `athletes.onboarding_complete` boolean exists from Phase 1.1. No Alembic revision is generated by this plan.
- Any LLM call or external HTTP call. The bootstrap is pure Python.
- Publication of the `onboarding_completed` event to the message bus. Event persistence happens in the producer transaction; publication belongs to the platform publisher worker (outside this plan).

## Architecture Contracts
- `01-entities/athlete.md` — DEPENDS ON (reads / writes `onboarding_complete` gate)
- `01-entities/athlete-profile.md` — DEPENDS ON (updates `timezone`, `structural_risk_flag`, optional `training_window`, preserves immutable `date_of_birth`/`sex`)
- `01-entities/athlete-preferences.md` — IMPLEMENTS (creation via the onboarding transaction, reads/patches via dedicated endpoints)
- `01-entities/training-goal.md` — IMPLEMENTS (creation within the onboarding transaction, restricted to `race_event` / `target_performance`)
- `01-entities/athlete-physiology.md` — IMPLEMENTS (creation with bootstrap posterior states)
- `01-entities/athlete-fitness.md` — IMPLEMENTS (creation with zero fitness/fatigue, population time constants)
- `01-entities/twin-state.md` — IMPLEMENTS (first append, `trigger = questionnaire`, `confidence_level = low`)
- `00-foundations/data-tiers.md` — DEPENDS ON (data-tier inference from `hr_source` + `power_source`; reuse the existing `infer_data_tier` helper)
- `00-foundations/confidence-model.md` — DEPENDS ON (bootstrap confidence = `low`; metric confidence initialised for `lt1.hr` / `lt2.hr` only)
- `01-entities/athlete-auth.md` — DEPENDS ON (Athlete must exist with authenticated credential for `require_self`)
- `04-platform/events.md` / `00-foundations/event-catalogue.md` → `onboarding_completed` — PRODUCES (via transactional outbox, ADR-004)
- `docs/adr/006-explicit-rollback-after-caught-db-exception.md` — DECISION (read before implementing; governs explicit `await session.rollback()` before raising domain errors after caught `IntegrityError`)

## Invariants
> The entire onboarding sequence runs in one database transaction. If any step fails, all prior steps roll back. When a database exception (e.g. `IntegrityError`) is caught and translated into a domain error, the catch block MUST call `await session.rollback()` before re-raising (see ADR-006). The athlete remains in `onboarding_complete = false` state.

> Event publication uses transactional outbox: `onboarding_completed` event inserted in same transaction as domain state; published after commit via outbox mechanism. Prevents phantom state visibility.

> `TwinBootstrapService` is pure Python. No LLM call, no external API call. Must complete within 200ms.

> Re-onboarding is not supported. Calling `POST /athletes/{id}/onboarding` when `onboarding_complete = true` returns 409. Athletes update preferences via PATCH.

> `TrainingGoal` enforces single active goal per athlete (409 on second creation).

> `AthleteProfile.structural_risk_flag` is computed from `AthletePreferences.sport_background`.

> Data tier is inferred from `hr_source` and `power_source` on `AthletePreferences`.

> Threshold estimates (`lt1_*`, `lt2_*`, `max_hr`) are bootstrapped from age-graded population norms using `AthleteProfile.date_of_birth`.

> `AthleteFitness` is initialised to zero fitness, zero fatigue.

> `TwinState.confidence_level = low`, `trigger = questionnaire`.

> TwinState is append-only — no `UPDATE` or `DELETE`. The bootstrap creates the first record; no subsequent step may modify it.

Required: `OnboardingAlreadyCompleteError` (HTTP 409), `AthleteNotFoundError` (HTTP 404), `OnboardingIncompleteError` (HTTP 409 when trying to read entities that only exist after onboarding), `TrainingGoalConflictError` (HTTP 409 when one active goal already exists), `InvalidGoalTypeError` (HTTP 422 for goal types outside `race_event` / `target_performance`).

3. [OWNER: Coder] Create `OnboardingService` taking `AsyncSession` and constructing the newly-built repositories plus the existing `AthleteRepository`, `AthleteProfileRepository` and `EventPublisher`. The service is the sole owner of the onboarding transaction. All entity creation happens via the repository methods (no direct `session.add` calls from the service body except through repository `add` wrappers). The service holds:
   - `async def complete_onboarding(athlete_id, prefs_input, goal_input, profile_input) -> OnboardingResult` — the atomic transaction.
   - `async def get_onboarding_status(athlete_id) -> OnboardingStatus` — returns `onboarding_complete`, whether the `TrainingGoal` exists, and whether the first `TwinState` exists.
   - `async def get_profile(athlete_id)`, `async def update_profile(athlete_id, patch)` — read/PATCH for `AthleteProfile` (mutable subset only: `height_cm`, `location_lat`, `location_lng`, `training_window`). Immutable fields (`date_of_birth`, `sex`, `timezone`) are silently rejected from PATCH with 422.
   - `async def get_preferences(athlete_id)`, `async def update_preferences(athlete_id, patch)` — read/PATCH for `AthletePreferences`. PATCH merges partial input at the field level (not JSONB-key level) except `weekly_schedule` which merges at the day level per the architecture note.
   - `async def get_twin_state(athlete_id)`, `async def get_twin_history(athlete_id, limit)` — thin wrappers over the `TwinStateRepository`. Return `None` / empty sequence when no record exists.

4. [OWNER: Coder] Implement the `complete_onboarding` method as a single atomic sequence. Ordering matters because of FK constraints:

   ```
   begin transaction (single AsyncSession shared by all repositories)
   ├─ reject with 409 if athlete.onboarding_complete == true
   ├─ validate goal input (race_event OR target_performance only; reject others with 422)
   ├─ validate timezone is non-null IANA identifier; reject with 422 if missing/invalid
   ├─ update AthleteProfile:
   │     set timezone, training_window (if supplied), structural_risk_flag
   │     structural_risk_flag = (sport_background != running_primary)
   ├─ create AthletePreferences (all fields from request)
   ├─ infer data_tier = infer_data_tier(hr_source, power_source)
   ├─ create TrainingGoal (status = 'active'; enforce one-active partial unique index, 409 on conflict)
   ├─ populate AthletePhysiology bootstrap:
   │     max_hr.value = 220 - age_in_years(dob)   (measurement_source = questionnaire_estimate)
   │     max_hr.prior_weight = 0.5
   │     lt1.hr.value = 0.75 * max_hr.value       (measurement_source = questionnaire_estimate)
   │     lt1.hr.prior_weight = 0.5
   │     lt2.hr.value = 0.875 * max_hr.value      (measurement_source = questionnaire_estimate)
   │     lt2.hr.prior_weight = 0.5
   │     all power / pace / cp / vo2max / max_hr.pace / max_hr.power = null
   │     set updated_at
   ├─ populate AthleteFitness bootstrap:
   │     aggregate = {fitness: 0.0, fatigue: 0.0, form: 0.0}
   │     aerobic / neuromuscular / structural = null
   │     time_constants = population defaults per architecture
   │        (aerobic: 42/7, neuromuscular: 21/3, structural: 56/14; source = population_default)
   │     last_activity_id = null
   ├─ populate TwinState bootstrap (append-only INSERT):
   │     data_tier = inferred tier
   │     confidence_level = 'low'
   │     trigger = 'questionnaire'
   │     model_version = 'v1-questionnaire-bootstrap'
   │     fitness = 0.0, fatigue = 0.0, form = 0.0
   │     lt1_pace_sec_per_km / lt1_power_watts / lt1_hr_bpm etc. inlined from physiology bootstrap
   │         (null for power / pace at bootstrap)
   │     cp_watts = null
   │     readiness_level = 'green'     (no wellness signal yet)
   │     wellness_trend = null
   │     metric_confidence = { lt1_hr: 'low', lt2_hr: 'low'; others null }
   │     training_goal_id = goal.id
   │     activity_id = null
   ├─ set athlete.onboarding_complete = true
   ├─ publish onboarding_completed(
   │       event_type='onboarding_completed',
   │       athlete_id=athlete_id,
   │       payload={
   │           training_goal_id, twin_state_id,
   │           data_tier=<int>, confidence_level='low'
   │       }
   │   ) via EventPublisher — this writes the SystemEvent and SystemEventOutbox rows in
   │   the SAME session as the producing transaction.
   └─ commit
   ```

   If any step raises, the transaction terminates without committing. When a database exception is caught and translated into a domain error, the catch block MUST call `await session.rollback()` before re-raising (ADR-006), returning the session to a clean state. When an exception propagates uncaught, SQLAlchemy's session teardown rolls back automatically. Partial state is never visible to other readers because `onboarding_complete` remains `false` until the final flip, after which it flips atomically with the commit.

## Event Contracts
`onboarding_completed` — PRODUCES.

Payload (v1):
```json
{
  "training_goal_id": "<UUID>",
  "twin_state_id": "<UUID>",
  "data_tier": 1..6,
  "confidence_level": "low"
}
```

Ordering assumption: `onboarding_completed` is published strictly after the producing transaction commits (per ADR-004). Consumers — `TrainingGoal` (no action, goal already created), `AthletePreferences` (no action, prefs already written), first-message agent in Phase 1.5a — observe only committed state.

The producer is `OnboardingService.complete_onboarding` calling `EventPublisher.publish(event_type='onboarding_completed', ...)` inside the same `AsyncSession` it commits at the end of the method. No out-of-band emission.

## Pseudocode

```
complete_onboarding(athlete_id, prefs, goal, profile):
    athlete ← get athlete by id (return 404 if missing)
    if athlete.onboarding_complete:
        raise OnboardingAlreadyCompleteError    // mapped to HTTP 409

    # Input validation
    validate goal.goal_type IN {race_event, target_performance}
    validate profile.timezone is IANA-valid
    validate per-goal-type required fields

    # Atomic write sequence (single DB session)
    profile_row       ← load AthleteProfile for athlete_id
    profile_row.timezone                ← profile.timezone
    profile_row.training_window         ← profile.training_window (if supplied)
    profile_row.structural_risk_flag    ← (prefs.sport_background != running_primary)

    prefs_row         ← new AthletePreferences(athlete_id, **prefs)
    add prefs_row

    goal_row          ← new TrainingGoal(athlete_id, status='active', **goal)
    add goal_row                           // unique partial index fires 409 on conflict

    age_years         ← years since profile_row.date_of_birth
    max_hr_est        ← 220 - age_years
    lt1_hr_est        ← round(0.75 * max_hr_est, 2)
    lt2_hr_est        ← round(0.875 * max_hr_est, 2)

    physio_row        ← new AthletePhysiology(
                            athlete_id,
                            lt1 = { hr: { value: lt1_hr_est, uncertainty: 1.0,
                                          prior_weight: 0.5,
                                          dominant_source: 'questionnaire_estimate',
                                          last_observation_date: today },
                                    power: null, pace: null },
                            lt2 = { hr: { value: lt2_hr_est, uncertainty: 1.0,
                                          prior_weight: 0.5,
                                          dominant_source: 'questionnaire_estimate',
                                          last_observation_date: today },
                                    power: null, pace: null },
                            cp = null, vo2max = null,
                            max_hr = { value: max_hr_est, uncertainty: 1.0,
                                       prior_weight: 0.5,
                                       dominant_source: 'questionnaire_estimate',
                                       last_observation_date: today }
                        )
    add physio_row

    fitness_row       ← new AthleteFitness(
                            athlete_id,
                            aggregate = {fitness: 0.0, fatigue: 0.0, form: 0.0},
                            aerobic = null, neuromuscular = null, structural = null,
                            time_constants = {
                                source: 'population_default',
                                aerobic:       { fitness_tau_days: 42, fatigue_tau_days:  7 },
                                neuromuscular: { fitness_tau_days: 21, fatigue_tau_days:  3 },
                                structural:    { fitness_tau_days: 56, fatigue_tau_days: 14 },
                                fitted_at: today
                            },
                            last_activity_id = null
                        )
    add fitness_row

    # inline snapshot
    data_tier         ← infer_data_tier(prefs.hr_source, prefs.power_source)
    twin_state        ← new TwinState(
                            athlete_id,
                            training_goal_id = goal_row.id,
                            activity_id = null,
                            data_tier, confidence_level='low',
                            trigger='questionnaire',
                            model_version='v1-questionnaire-bootstrap',
                            fitness=0.0, fatigue=0.0, form=0.0,
                            lt1_hr_bpm=lt1_hr_est, lt2_hr_bpm=lt2_hr_est,
                            lt1_pace_sec_per_km=null, lt2_pace_sec_per_km=null,
                            lt1_power_watts=null, lt2_power_watts=null,
                            cp_watts=null,
                            readiness_level='green', wellness_trend=null,
                            metric_confidence={ lt1_hr: 'low', lt2_hr: 'low',
                                                lt1_power: null, lt1_pace: null,
                                                lt2_power: null, lt2_pace: null,
                                                cp: null }
                        )
    insert twin_state                      // append-only

    athlete.onboarding_complete ← true

    publish_onboarding_completed(
        athlete_id,
        payload = {
            training_goal_id: goal_row.id,
            twin_state_id:    twin_state.id,
            data_tier:        int(data_tier),
            confidence_level: 'low'
        }
    )

    commit transaction
    return OnboardingResult(twin_state, goal_row, data_tier)
```

## Testing Requirements
- **Exit — atomic success:** Submitting a complete onboarding request with `race_event` goal creates exactly one `TrainingGoal` (status = `active`), one `AthletePhysiology`, one `AthleteFitness`, one `TwinState`, one `AthletePreferences`, and flips `athlete.onboarding_complete` to `true` within a single committed transaction.
- **Exit — onboarding_completed event:** The `onboarding_completed` `SystemEvent` row exists for the athlete with the documented payload (`training_goal_id`, `twin_state_id`, `data_tier`, `confidence_level = 'low'`) and a paired `SystemEventOutbox` row with `status = 'pending'`, both persisted in the same transaction as the domain state.
- **Exit — mid-transaction rollback:** Force a failure at any of the entity-creation steps (e.g. corrupt JSONB for `lt1`) and assert: no `AthletePreferences`, `TrainingGoal`, `AthletePhysiology`, `AthleteFitness`, or `TwinState` rows exist for the athlete; `onboarding_complete` is still `false`; no `onboarding_completed` event row exists.
- **Exit — idempotency guard:** Calling `POST /athletes/{id}/onboarding` a second time for the same athlete returns `409`; no new rows are written; no new outbox row is added.
- **Exit — TwinState correctness:** `GET /athletes/{id}/twin` after onboarding returns confidence_level = `low`, `trigger = questionnaire`, `fitness = 0`, `fatigue = 0`, `form = 0`, non-null `lt1_hr_bpm` and `lt2_hr_bpm` derived from the athlete's DOB via the documented formulae, `readiness_level = green`, `data_tier` matching `infer_data_tier(hr_source, power_source)`, `activity_id = null`.
- **Exit — data tier wiring:** `infer_data_tier` produces the expected tier for every `{hr_source, power_source}` combination documented in `00-foundations/data-tiers.md`. The value appears on `TwinState.data_tier` exactly.
- **Exit — goal-type restriction:** Submitting `goal_type = 'fitness_improvement'` / `'maintenance'` / `'recovery'` returns `422`; submitting `target_performance` without `target_distance_km` and `target_time_minutes` returns `422`; submitting `race_event` without `goal_event_type` / `goal_event_date` returns `422`.
- **Exit — single-active-goal invariant:** A second `complete_onboarding` call for the same athlete (via a separate test setup that bypasses the `onboarding_complete` gate to test the partial unique index independently) raises `TrainingGoalConflictError` mapped to `409`.
- **Exit — profile PATCH guard:** PATCHing an `AthleteProfile` after onboarding with `date_of_birth`, `sex`, or `timezone` in the body returns `422` and the stored values are unchanged; PATCHing only mutable fields (`height_cm`, `location_lat`, `location_lng`, `training_window`) updates `updated_at` and the patched values are returned.
- **Exit — preferences PATCH merge:** PATCHing `weekly_schedule` with only `{saturday: {available: false}}` flips Saturday without touching other days.
- **Exit — twin / profile read before onboarding:** GET endpoints for `profile`, `preferences`, `twin`, `twin/history` return `200` (empty profile) or `404` (preferences / twin / twin history) before onboarding is complete; they return the populated records after onboarding completes.
- **Exit — cross-athlete access:** Every endpoint returns `403` (never `404`) when the JWT athlete_id does not match the path `athlete_id`, using the existing `require_self` dependency.

- **No migration.** All six tables (`athletes`, `athlete_profiles`, `athlete_preferences`, `training_goals`, `athlete_physiology`, `athlete_fitness`, `twin_states`) already exist at head revision `d1579f4430e7`. Do NOT create a new Alembic revision. Verify the head matches before running.
- **Transaction pattern.** `complete_onboarding` must use the same `AsyncSession` for every repository call and commit exactly once at the end of the method. Raising any exception before the commit prevents the commit. Match the pattern established by `AuthService.register`, including the order: do work → `events.publish(...)` → `session.commit()`. When a database exception (e.g. `IntegrityError` on `training_goals.add`) is caught and translated into a domain error, the catch block MUST call `await session.rollback()` before re-raising (ADR-006). This returns the session to a clean state at the point of translation; it is NOT redundant — it is required. See `docs/adr/006-explicit-rollback-after-caught-db-exception.md`.
- **Event persistence.** Use the existing `EventPublisher.publish(...)` helper inside the transaction. It writes `SystemEvent` + `SystemEventOutbox` rows in the same session. Publication to the message bus is out of scope — the publisher worker handles that after commit.
- **`AthleteProfile` is an update, not a create.** The profile row was created during `POST /auth/register` (Phase 1.1). Onboarding only enriches it with `timezone`, `training_window` (if provided), and the computed `structural_risk_flag`. Never `add()` a second profile for the same athlete — doing so will violate the unique constraint on `athlete_id`.
- **Structural risk flag computation.** `structural_risk_flag = (prefs.sport_background.value != 'running_primary')`. Compute it inside the service; never trust the client.
- **Data tier.** Reuse the existing `infer_data_tier` helper from `app.models.athlete_preferences`. It returns `DataTier.TIER_…` int-enums; persist the `.value` (integer) on `TwinState.data_tier`.
- **Physiology bootstrap shapes.** The JSONB shape inside `lt1`, `lt2`, `cp`, `vo2max`, `max_hr` mirrors what `PhysiologyUpdateService` (Phase 1.6) will write in place. Match the nested shape exactly: `{value, uncertainty, prior_weight, dominant_source, last_observation_date}` where `dominant_source = 'questionnaire_estimate'` for bootstrap rows. `cp` and `vo2max` are `null` at bootstrap (never estimated from the questionnaire — architecture invariant).
- **Fitness bootstrap shape.** Use aggregate-only: `{fitness: 0.0, fatigue: 0.0, form: 0.0}`. Dimensional blocks (`aerobic`, `neuromuscular`, `structural`) must be `null`. The `time_constants` JSONB must include `source = 'population_default'` and the three dimension tau values per architecture. The CHECK constraint `form = fitness - fatigue` on `aggregate` fires at commit time — keep `form` consistent.
- **TwinState append-only.** The `TwinStateRepository` must expose only `insert`, `get_latest`, `get_history`, `get_by_activity`. No `update()` / `delete()` methods — the repository contract is part of the architecture invariant.
- **Metric confidence bootstrap.** Only `lt1_hr` and `lt2_hr` are populated at bootstrap, both `low`. All other metric confidence keys are `null` (not missing — explicitly `null` in the JSON). Global `confidence_level = min(lt1_hr, lt2_hr) = 'low'`.
- **`activity_id` stays `null`.** The `questionnaire` trigger has no triggering activity. The partial unique index on `(athlete_id, activity_id) WHERE activity_id IS NOT NULL` intentionally allows any number of non-activity-triggered TwinStates per athlete.
- **Timezone validation.** Use Python's standard library (`zoneinfo.ZoneInfo`) to validate the IANA timezone. Reject invalid identifiers with a 422 before writing any row. Timezone is immutable on AthleteProfile after creation — the PATCH endpoint must refuse it explicitly.
- **PATCH idempotency.** PATCH `/preferences` and `/profile` must be idempotent: re-applying the same patch yields the same database state and the same response shape. `weekly_schedule` specifically merges at the day level per the architecture note (`{saturday: {available: false}}` flips only Saturday).
- **TrainingGoal immutability fields.** The TrainingGoal PATCH in this plan is not implemented (deferred to 1.4+). Only the onboarding creation endpoint is in scope. Do not create a training-goal management endpoint here.
- **Goal-type whitelist.** Even though `GoalType` has five enum values, only `race_event` and `target_performance` are permitted at onboarding. Reject the others with `InvalidGoalTypeError` → 422. This is the same rejection the architecture document describes for Tier 3 (questionnaire-only) path.
- **`require_self` on every endpoint.** All eight endpoints require `require_self` to enforce JWT athlete_id === path athlete_id; 403 (never 404) on mismatch.
- **Router registration.** Register `onboarding_router` under `api_router` in `app/api/v1/__init__.py`. Follow the `auth_router` pattern — no additional middleware; error mapping lives in the per-endpoint body.
- **Error mapping pattern.** Catch `OnboardingAlreadyCompleteError`, `TrainingGoalConflictError`, `AthleteNotFoundError`, `OnboardingIncompleteError`, `InvalidGoalTypeError` at the router layer and translate to HTTP 409 / 404 / 422. Match the `auth.py` pattern for consistency.
- **Registration hygiene.** Don't forget to export every new class (repository, service, error, schema, router) through the relevant `__init__.py`. The implemented-state snapshot verifies completeness of registrations and the Test Architect's manifest will fail on missing symbols.
- **Suggested step order.** Steps 1 → 2 → 3 → 4 → 5 → 6 → 7 are sequential: repositories first, errors next, service next (uses repositories + errors), schemas next (parallel to service writing actually), router next, registrations last. Schema writing (Step 5) can proceed in parallel with Step 4 if that helps the coder stay in flow.

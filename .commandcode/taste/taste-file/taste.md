# Taste File
- Always reference the official OpenCode documentation at https://opencode.ai/docs/ and its subpages (agents, tools, skills, etc.) when working on OpenCode-related tasks. Confidence: 0.90
- Search for community/industry best practices around skills, subagents, and agents when designing OpenCode architectures — don't rely solely on official docs. Confidence: 0.85
- Role is OpenCode prompt/skill/subagent architect — the user builds and maintains sophisticated multi-agent OpenCode setups with delegation graphs, skill extraction, permission patterns, and model routing. Confidence: 0.80
- In OpenCode agent architectures, agents whose filenames start with `p-` are primary agents, never subagents. The naming prefix encodes the agent's role in the delegation graph. Confidence: 0.98
- Avoid duplication between agent prompts and skills: each concept lives in exactly one place. Agent prompts own process flow (which step does what, in what order). Skills own templates, content rules, and definitions. When both need the same information, the agent prompt delegates to the skill with a concise pointer rather than repeating the content. Confidence: 0.90
- Subagent prompts should minimize MCP/tool calls by using decision-tree patterns (one primary tool drives conditional follow-ups) rather than sequential checklists that encourage running every available tool. Confidence: 0.90
- Use the `steps:` field in subagent frontmatter to cap model turns and prevent runaway tool-calling loops. Confidence: 0.70
- For subagents that legitimately require many MCP calls to fulfill their purpose (e.g., impact analysis), avoid restrictive `steps:` limits — they block the agent from completing its work. Use `steps:` as a runaway-loop guard, not a tight budget. Confidence: 0.80

- Before modifying a subagent's behavior or tool-calling pattern, always first analyze the call sites — grep for every context where the subagent is invoked and confirm what callers actually expect. Base optimization decisions on what callers need from the output, not on what the subagent's current prompt instructs it to run. Confidence: 0.88
- When reducing subagent tool calls, completeness of the output takes priority over minimizing calls — never skip a section that a caller genuinely needs. Optimize for the minimum set of calls that still produces a complete report, not the absolute minimum calls possible. Confidence: 0.85
- When fixing a subagent's tool-calling behavior, fix both sides of the delegation contract: the subagent's prompt (what it does) AND the calling agents' prompts (what they ask for). Don't optimize one side in isolation — mismatched expectations between caller and subagent are the root cause of both over-calling and under-reporting. Confidence: 0.80
- When debugging subagent behavior or building a case for optimization, always verify with actual return values from session traces — never infer what a tool "should" have returned based on its name or purpose. A claim like "get_change_impact returned the data" must be backed by showing the actual response. Guessing leads to wrong root-cause analysis. Confidence: 0.92
- When proposing changes, explain what you propose and why before executing — don't jump straight to editing. The user wants to understand the reasoning and validate the approach before any code or config is modified. This applies especially to agent prompt changes where the reasoning reveals whether the diagnosis is correct. Confidence: 0.88

- When an agent family has multiple modes that share substantial instruction blocks (meta-instructions, standards, contracts), extract a shared-core skill following the `{family}-shared-core` naming pattern. Each mode keeps only mode-specific dispatch logic; the shared core is loaded on demand. This avoids maintaining the same content across multiple agent prompts. Confidence: 0.85

- Before splitting one agent into multiple agents, verify that the existing skill/modality isolation within a single agent isn't already sufficient. A separate agent adds ceremony — its own frontmatter block, permission set, REGISTRY row, and delegation path — that must be justified by clear value beyond what a mode-specific skill loaded by the original agent already provides. Confidence: 0.80

- Avoid concrete real-world examples in agent/subagent prompts and skill documentation. Use generic, abstract descriptions of behavior patterns instead. Real examples (class names, entity names, symbol names from the actual codebase) create anchors that skew the agent's behavior — it overfits to the example rather than generalizing to the caller's actual input. Confidence: 0.90
- When verifying skill names, directory names, or file existence within the project, always check the actual filesystem (glob, ls) rather than relying on cached or stale knowledge from prior sessions. The filesystem is the source of truth; names may have been renamed since the last observation. Confidence: 0.85
- Skill files scoped to a specific agent family should be prefixed with that family's name (e.g., `coder-` for skills used by `p-coder-*` agents). This namespaces skills by their consumer and makes the ownership boundary visible at a glance. Confidence: 0.90
- In agent prompts, subagent invocation instructions should use compact inline format (e.g., `- s-doc-explorer → Task: <description> | Concepts: <list> | Domains: all`) rather than verbose fenced `Tool: task` code blocks. The inline format is scannable, saves ~75% of the vertical space, and still conveys the subagent name, prompt variables, and when to use it. Confidence: 0.88
- When renaming a skill, subagent, or any named entity that other files reference, fix every stale reference across the entire project in the same change batch — agent files, REGISTRY.md, FINDINGS.md, and any other agent rows that list it. Don't leave the registry or other agents pointing to old names. Confidence: 0.85

- In multi-mode agents, keep mode boundaries clean: one mode should not consume artifacts produced by a different mode unless there is an explicit, documented handoff contract between them. The default expectation is that each mode is self-contained. Cross-mode artifact loading (e.g., Generate Mode reading a stale DevOps report) adds conditional complexity that needs strong justification — "defense-in-depth against an improbable case" is not enough. Confidence: 0.85
- In shared-core / mode-protocol architectures, when the shared core references a skill as a dependency, every mode-specific protocol or procedure that needs that skill must contain its own explicit "load now" instruction at the appropriate execution point. A passive reference in the shared core is not sufficient — the concrete load directive must live in the execution path, not just be implied. Confidence: 0.85
- Apply the same architectural patterns to analogous agent families. When one family (e.g., coder) uses a shared-core + separate mode-agents split, other families with the same multi-mode structure should follow suit. The user expects architectural consistency across the system — don't defend one pattern for one family and the opposite for another. Confidence: 0.85
- When the user points out that your reasoning contradicts a pattern already established elsewhere in the system, acknowledge the inconsistency directly and adopt the consistent approach. Don't defend the original position — the user values reasoning that generalizes. Confidence: 0.82

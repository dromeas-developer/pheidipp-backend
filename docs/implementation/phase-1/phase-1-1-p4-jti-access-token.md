# Implementation Plan: Phase-1.1-P4 — JWT jti Claim for Access Token Uniqueness
## Plan ID: Phase-1.1-P4

## Sub-Phase Reference
Sub-Phase ID: Phase-1.1
Sub-Phase Title: Phase 1 — Email/Password Authentication

## Objective
Patch the Phase-1.1 authentication implementation so every newly issued access token contains a unique `jti` claim. This removes deterministic JWT equality when registration/login/refresh issues multiple tokens within the same second, while preserving the existing stateless access-token model and refresh-token rotation behaviour.

## Scope
- Add a per-issuance `jti` claim to access tokens generated by `TokenService.issue_access_token()`.
- Keep access-token signing, verification, expiry, `athlete_id`, `iss`, and optional `auth_provider` behaviour unchanged.
- Keep `jti` inside the JWT only; do not expose it as a separate API response field.
- Keep access-token verification stateless and compatibility-preserving for already-issued tokens.
- Update unit, integration, and API tests to assert `jti` presence and uniqueness on newly issued tokens.
- Record the architecture clarification that `jti` is a per-issuance UUID and is not a replay ledger.

## Out Of Scope
- Persisting `jti` values in the database.
- Rejecting replayed access tokens based on `jti`.
- Changing refresh-token rotation, refresh-token hashes, or refresh-token revocation semantics.
- Changing API response schemas, HTTP status codes, or user-facing auth errors.
- Adding OAuth providers, account linking, email verification, password reset, rate limiting, or onboarding.
- Creating a migration, because this plan changes only JWT claim content and tests.

## Invariants
- JWT claims include `jti`, `iat`, `exp`, `iss`, `athlete_id`, and optionally `auth_provider`.
- The `jti` claim is a per-issuance UUID used to make each JWT value unique even when issued within the same second; it is not persisted or checked as a replay ledger.
- The `auth_provider` claim is informational and does not affect authorization logic.
- Refresh tokens are rotated on every use — old token is revoked atomically with new token creation.
- `RefreshToken` records are append-only revocation records; rotation revokes the old token and inserts a new token record.
- `token_hash` is never returned by any API endpoint or included in any log.
- `hashed_password` is never returned by any API endpoint or included in any log.
- The `require_self` FastAPI dependency validates `JWT.athlete_id === path.athlete_id`. It does not validate auth provider — all providers use the same authorization model.

## Implementation Steps
1. Update access-token issuance so every call to `TokenService.issue_access_token()` creates a fresh `jti` claim using a random UUID and includes it in the signed JWT payload.
2. Preserve stateless access-token verification:
   - Continue verifying signature, issuer, `iat`, `exp`, and athlete identity.
   - Decode and ignore `jti` if present.
   - Do not reject already-issued tokens solely because they lack `jti`.
   - Do not add database lookup or replay detection for `jti`.
3. Do not change API response schemas or response builders; the access token remains returned as the existing `access_token` string.
4. Update unit tests for `TokenService.issue_access_token()` to assert:
   - newly issued tokens contain a `jti` claim;
   - `jti` is parseable as a UUID;
   - two tokens issued for the same athlete within the same second have different `jti` values and different encoded JWT values.
5. Update service-level rotation tests to assert the refreshed/rotated access token has a different `jti` from the original access token, rather than relying only on whole-token inequality.
6. Update API refresh tests similarly: decode both access tokens and assert the refreshed access token carries a different `jti`.
7. Run the auth feature test group and confirm the deterministic-access-token failures from the devops report are resolved without regressions to refresh-token rotation, `require_self`, or secret exclusion.

## Pseudocode
```text
issue_access_token(athlete_id, auth_provider?)
  now = current UTC time
  exp = now + access_ttl
  jti = random UUID

  claims = {
    sub: athlete_id,
    athlete_id: athlete_id,
    iat: now as integer seconds,
    exp: exp as integer seconds,
    iss: configured issuer,
    jti: jti
  }

  if auth_provider is present:
    claims.auth_provider = auth_provider

  sign claims with JWT secret
  return signed token, exp

verify_access_token(token)
  decode and verify signature, issuer, and expiry
  if jti is present:
    ignore it for authorization and replay decisions
  return athlete identity and token validity claims
```

## Testing Requirements
- `tests/unit/test_token_service.py` verifies that every newly issued access token contains `jti`.
- `tests/unit/test_token_service.py` verifies that `jti` is a valid UUID string.
- `tests/unit/test_token_service.py` verifies that two access tokens issued for the same athlete within the same second have different `jti` values and different encoded JWT strings.
- `tests/integration/test_auth_service.py::test_rotation_returns_new_token_pair` verifies that refresh rotation returns a new refresh token and a new access token with a different `jti`.
- `tests/api/test_auth_endpoints.py::test_refresh_returns_new_token_pair` verifies that `POST /auth/refresh` returns a new refresh token and an access token with a different `jti`.
- Existing `require_self` tests continue to pass: valid token with matching athlete returns 200, mismatched athlete returns 403, malformed or expired token returns 401.
- Existing secret-exclusion tests continue to pass: no `hashed_password`, `token_hash`, raw refresh token, `provider_tokens`, or `provider_user_id` appears in API responses.

## Coder Handoff Notes
- This is a focused patch. Do not broaden it into replay protection or access-token revocation.
- `jti` uniqueness is about JWT value uniqueness, not replay prevention. The architecture explicitly keeps access tokens stateless.
- Do not persist `jti`, add a `jti` table, add a unique index, or query the database during access-token verification.
- Do not expose `jti` as a separate response field. It belongs inside the JWT payload only.
- For backward compatibility, already-issued tokens without `jti` may remain valid until their existing expiry.
- The architecture document was already clarified to include `jti` and to state that it is not a replay ledger; read that clarification before implementing.
